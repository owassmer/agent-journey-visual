# Jev pivot: understanding, implications and what changes

## Context
Steps 1–3 are merged: the runtime smoke test, dated evidence snapshots and the finance core. `Jev_Pivot.md` redefines step 4 and re-plans steps 5–7. The old step 4 treated Jev as an optional tool the agent calls on (`judge_evidence` with agent-chosen question IDs). The pivot makes Jev a **semantic judgment layer**, applied systematically wherever text turns into a fact, a fact into an economic effect, or evidence conflicts. The layer is host-controlled and recorded in one immutable investigation graph, and the UI, reviewer and evaluator all consume that graph.

This document confirms my understanding before any file changes, and lists exactly what should change.

## My read of the pivot (thesis)
*Claude thinks broadly, Jev judges narrowly, code computes exactly, the host controls everything, and the reviewer sees the causal chain.*

Jev earns its place by **preventing category errors before they become financial inputs**. Examples: an allegation treated as a liability, a paid matter treated as a future outflow, a noncash gain treated as cash, the wrong entity, a disputed demand treated as a payment. It does not predict risk, and it never sets amounts, dates or decisions.

The graph (source → Jev observation → atomic finding → effect proposal → engine result) is the product's audit trail, so it has to be recorded now rather than reconstructed later.

## Unchanged (non-negotiables the pivot reinforces)
- Jev confidence is never a probability, a weight or a haircut, and a Jev answer never activates a cash adjustment automatically.
- Dates, arithmetic, double-count protection and cash conservation stay in `app/finance` (merged step 3).
- Snapshot isolation stays as it is (step 2 `EvidenceStore`). The agent never passes paths, cutoffs or raw Jev state. Evaluator and facts files never reach the agent, Jev or the reviewer.
- The deliverable remains a financing decision plus the loan's dated cash flows.

## Where I agree, refine or push back
1. **The screen labels and orders evidence; it never hides it.** `candidate_screen` routes FTS results into direct evidence, conflict, and context-only. A Jev false negative must not bury the passage that answers the question, so every candidate stays visible to the agent with its label, and screened-out IDs stay readable.
2. **Host-triggered, not agent-optional.** Two points in the flow become automatic host operations: search triggers the candidate screen, and proposing a finding triggers the finding check. Claim interpretation and statement relation stay agent-requested, but through **profiles plus object IDs**, and the host builds the minimal state. This does not violate the spec §7 rule against a "fixed Jev-question sequence": that rule forbids answer-bearing scripts, and the agent still chooses the research strategy. The spec wording needs updating to say so explicitly.
3. **Provider provenance: not adopted (your decision).** The pivot's "fix provider provenance" section, meaning the demo/evaluation provider policies, any eval-mode freeze, and direct TypeSafe, is out of scope. The adapter keeps its current behaviour: the OpenRouter route, the returned model recorded on every judgment, and the existing model check. It is not raised in PRs or reports.
4. **Honest attempt accounting (budget, not provenance).** The budget counts physical attempts including SDK retries, but the adapter counts calls while the SDK silently retries up to 2 times. The fix is to set the `RetryPolicy` explicitly and reserve 1 + max_retries attempts per call against the ceiling.
5. **Jev budget (decided): 150 physical attempts per run, spend cap unchanged at $0.10.** Per-candidate screening is one request per query–passage pair, about 100–150 per run, which costs about $0.01. Use the async client for parallel fan-out to protect the 600 s wall clock.
6. **Runtime effects cite findings and spans, never kit fact IDs.** The kit's `economic-effects.json` cites the evaluator-only facts registry. Runtime `EconomicEffectProposal`s must cite `AtomicFinding` IDs and exact source spans: `section_id` plus char offsets plus a quote that the host verifies verbatim against the stored section text. That verbatim check is a deterministic provenance guard worth adding.
7. **`economic_role` bridges to the mechanisms.** It maps onto the spec §5 mechanism families: existing cash obligation → settlement payment or resolved obligation; noncash accounting item → normalization (never a ledger stream); cash-access constraint → restricted funds; operating change → interruption or receipt delay; financing or reimbursement → expense funding. It is a warning and routing signal; host validation keeps authority.
8. **Keep, but de-emphasize.** `instruction_like_text` stays cheap and invisible. `next_source` and `candidate_relevance` are retired from the profiles, because `gap_relevance`, `usable_evidence` and `premise_conflict` replace them. Score is not used.
9. **Deadline realism.** The pivot's step 4 is roughly 2–3× the old one. Semantic eval labels are evaluation data, not a test suite; a small labelled set (about 15–20 boundary cases from both borrowers) is enough to sanity-check the 0.5 routing thresholds, with no automatic confidence gates.
