A TypeSafe Jev model watches the Kuru MON-USDC order book and answers buy or sell every ~300 ms. Every block posts a real post-only limit order on that side, one tick inside the touch, replacing the last one. Fills happen when a taker hits it, so the bot earns the spread instead of paying it. A small server streams every block to the dashboard.\nL179: ## Run\nL180: \nL181:     `cp .env.example .env\nL182:     bun install\nL183:     bun run start\nL184:     `\nL185: \nL186: With no `PRIVATE_KEY` it dry-runs: real book, real decisions, simulated fills. Set `MODEL=jev` and `TYPESAFE_AI_API_KEY` to use Jev; the default `mock` is a momentum heuristic stand-in.\nL187: ## Endpoints\nL188: \nL189: Deployed (dry run, mock model): \ue200cite\ue20290\u2020https://jev-trader-production.up.railway.app\u2020jev-trader-production.up.railway.app\ue201 L190: \nL191:   * `GET /` snapshot: model, wallet, dryRun, latest block event\nL192:   * `GET /history` last 1000 block events\nL193:   * `GET /events` SSE: `snapshot` on connect, then one `block` event per block, plus a `fill` event whenever a live order's receipt lands\nL194: Every event (see `src/trader.ts` for types):\nL195: \nL196:     `{\nL197:       \"block\": 105488269, \"ts\": 1789593630676,\nL198:       \"mid\": 0.022636, \"bestBid\": 0.022628, \"bestAsk\": 0.022644, \"spreadBps\": 7.07,\nL199:       \"decision\": { \"action\": \"buy\", \"probabilities\": { \"buy\": 0.77, \"sell\": 0.23, \"hold\": 0 }, \"upIn10\": 0.77, \"latencyMs\": 81, \"late\": false },\nL200:       \"quote\": { \"side\": \"buy\", \"price\": 0.022629, \"size\": 200, \"txHash\": \"0x\u2026\", \"gasMon\": 0.0357, \"cancel\": [100295801], \"status\": \"sent\", \"orderId\": null, \"capped\": false },\nL201:       \"fill\": null,\nL202:       \"resting\": { \"bidMon\": 200, \"askMon\": 200 },\nL203:       \"position\": { \"side\": \"short\", \"size\": 200, \"entryPrice\": 0.022633, \"unrealizedUsd\": -0.0006, \"unrealizedMon\": -0.027 },\nL204:       \"totals\": { \"blocks\": 3, \"decisions\": 3, \"quotes\": 3, \"fills\": 1, \"reverted\": 0, \"lateBlocks\": 0, \"jevUsd\": 0.000004, \"gasMon\": 0.107, \"gasUsd\": 0.0024, \"realizedUsd\": 0, \"pnlUsd\": -0.003, \"pnlMon\": -0.13, \"pnlPct\": -0.003 }\nL205:     }\nL206:     `\nL207: Every block the model is asked about the move over `HORIZON_BLOCKS` (default 100, ~30 s) and answers `buy` or `sell`. `quote` is the order that block put on the book: a post-only limit order of `TRADE_SIZE_MON` on that side, `QUOTE_INSIDE_TICKS` inside the touch (clamped to the touch when the spread is too tight), in one `batchUpdate` that also cancels everything we had resting (`cancel`). `hold` appears only with `decision.late: true`, when the model missed the block and nothing was posted.\nL208: When the position cap (or, live, margin funds) blocks a side, the quote goes on the other side with `capped: true` and `probabilities` still show the model's call. `resting` is our size known to be on the book after this block. `upIn10` equals the buy probability.\nL209: Live sends are fired and forgotten, so the `block` event carries the intent: `status: \"sent\"`, `gasMon` is `gasLimit x (last known base fee + priority)`. Monad charges the gas limit, so that is the real cost whether the order lands or not. The receipt arrives a block or two later as its own SSE event:\nL210: \nL211:     `event: quote\nL212:     data: { \"block\": 105488269, \"quote\": { \u2026, \"status\": \"placed\", \"orderId\": 100295812, \"gasMon\": 0.0357 } }\nL213:     `\nL214: `status` becomes `placed` (with the order id) or `reverted` (the book moved through the price before the tx landed, or a cancelled order had already filled). No receipt after 10 blocks gives `lost`. Fills are not in our own transactions: someone else's taker order hits our resting one, and the Trade log for it arrives via the same `eth_getLogs` poll that feeds the model. Each block with fills gets its own SSE event, and `position`, `realizedUsd` and `fills` update then:\nL215: \nL216:     `event: fill\nL217:     data: { \"block\": 105488271, \"fill\": { \"side\": \"buy\", \"size\": 200, \"price\": 0.022629, \"txHash\": \"0x\u2026\", \"orderId\": 100295812, \"simulated\": false } }\nL218:     `\nL219: `txHash` is the taker's transaction. In a dry run the quote is `status: \"sim\"`: the order rests for one block and a real print crossing its price fills it (`simulated: true`).\nL220: ## Layout\nL221: \nL222:     `src/config.ts   env\nL223:     src/chain.ts    block feed (WebSocket newHeads + polling backstop, newest block only), raw RPC\nL224:     src/book.ts     one-eth_call order book reader (decodes getL2Book, merges the AMM vault)\nL225:     src/market.ts   Kuru: read book, hand-encoded batchUpdate (cancel + post-only place), margin deposits, local nonce, async confirmation\nL226:     src/model.ts    Model interface, JevModel (AI SDK experimental_evaluate), MockModel\nL227:     src/trader.ts   the loop: one in flight, hold when late, position and P&L accounting\nL228:     src/server.ts   Bun.serve: snapshot, history, SSE\nL229:     `\nL230: ## The 300 ms budget\nL231: A decision and an order have to fit in one block, so the hot loop makes exactly two RPC round trips: one `eth_call` for the book (~18 ms on the public RPC, `READ_RPC_URL`) and one `eth_sendRawTransaction` (`RPC_URL`), which returns as soon as the tx is accepted.\nL232: Nothing else is on the path \u2014 no `eth_estimateGas` (Monad charges gas on the limit, so the limit is hardcoded or derived once at startup), no `eth_sendRawTransactionSync` (it blocks until the tx is Proposed), no gas price lookup (static type-2 fees: `MAX_FEE_GWEI` cap, 2 gwei priority; the effective price is base + priority). \ue200cite\ue20291\u2020MIT license\ue201 L175: \nL176: More items\nL177: # jev-drone\nL178: \nL179: An autonomous quadrotor flies a five-station obstacle course in MuJoCo using only its onboard camera. A small judgment model (\ue200cite\ue20292\u2020TypeSafe\u2020typesafe.ai\ue201 's Jev) sits at ~2.5 Hz and decides what the situation means; everything time-critical stays in ordinary code.\nL180: \nL181: The drone is the Skydio X2 from \ue200cite\ue20293\u2020MuJoCo Menagerie\ue201 L182: \nL183:   * a real airframe with four rotors, flown by a geometric controller. Nothing about the flight is scripted.\nL184: ## The idea\nL185: Jev is not a vision model. It takes JSON and returns typed answers with probabilities. So it cannot be the perception layer, and it cannot run at control rate. What it can do is answer small questions about a situation that ordinary code finds hard to phrase.\nL186: \nL187:     ` 500 Hz   geometric controller       flight.Pilot    thrust-priority mixing, slew-limited\nL188:       50 Hz   guidance + safety reflex   run.Guidance    ALWAYS owns safety\nL189:       15 Hz   camera -> symbolic scene   flight.Eye      depth + segmentation, no ground truth\nL190:     ~2.5 Hz   tactical judgment          tactics.py      Jev, advisory only\nL191:     `\nL192: Classical CV turns the depth and segmentation buffers into a compact scene: five forward range sectors, the height of whatever is blocking the path, whether its top edge is even visible, and where the target is. Jev reads that and answers three questions in one call:\nL193: question  | type  | options\nL194: --- | --- | ---\nL195: `maneuver`  | Choice  | hold_course / gap_left / gap_right / climb / brake / reacquire\nL196: `risk`  | Score  | clear and open -> tight -> about to hit something\nL197: `target_truly_lost`  | Noul  | genuinely lost, or just briefly occluded?\nL198: Code decides when to ask. On an open corridor with the target in view there is nothing to decide, so no call is made. Scenes are fingerprinted so an unchanged situation reuses the last judgment. A typical 65 s flight costs about 110 calls.\nL199: \nL200: Code keeps the veto. A hard reflex layer runs at 50 Hz and overrides any judgment when something is close. Jev can propose `climb`, but code refuses it unless the obstruction's measured top edge is actually within the aircraft's climb ceiling.\nL201: ## The course\nL202: \nL203: Five stations, each breaking a different assumption:\nL204: \nL205:   1. Slalom - ordinary steering around pillars\nL206:   2. Low beam - spans the whole corridor. No lateral gap exists at any width, so \"go around\" is not available. It must be flown over.\nL207:   3. Turnstiles - arms sweeping across the lane. Moving, must be timed.\nL208:   4. Sliding gate - a 3.2 m gap that slides sideways. Too tall to climb, so it must be threaded.\nL209:   5. Cluster - dense pillars\nL210: ## Results\nL211: \nL212: The ablation is the same stack with the Jev call disabled, falling back to a greedy \"steer toward the wider side\" heuristic. That baseline is safe but stuck: it never crashes and it never gets past station 2, because going over an obstacle is not something it can express.\nL213:  | baseline (no Jev)  | Jev engaged\nL214: --- | --- | ---\nL215: furthest point reached  | 17.7 / 17.7 / 17.7 m  | 77.5 m (whole course)\nL216: target kept in view  | ~19%  | 82%\nL217: time pinned in reflex  | 65-71%  | 9%\nL218: collisions  | 0 / 0 / 0  | 0\nL219: The baseline stops dead at station 2 every single time. With Jev the drone clears the entire course in about 47 s at up to 3.6 m/s:\nL220: \nL221:     `x=19  beam0       t=15.7  z=3.0   climbed over\nL222:     x=26  turnstiles  t=20.3  z=1.6   timed the sweeping arms\nL223:     x=38  GATE        t=31.3  z=1.6   threaded the sliding 3.2 m gap\nL224:     x=44  beam1       t=36.8  z=2.8   climbed over\nL225:     x=50  cluster     t=41.3  z=1.6   lost the rover in the pillars\nL226:     x=58  exit        t=46.6          re-acquired it and closed back to 3.7 m\nL227:     `\nL228: 80 calls over 65 s, 0.11 s median latency, 96k tokens.\nL229: \nL230: The cluster is worth noting: the drone genuinely loses the rover there, flies to where it estimates the rover has got to, and picks it back up. That recovery is the difference between a demo and a system.\nL231: Honest caveats. The Jev column is a single 65 s run, not a seed-matched average. On an earlier, simpler arena a matched 3-seed comparison showed no advantage for Jev (it crossed 0/3, same as baseline) - the extra maneuvering cost target visibility. Run-to-run variance is large. The claim this repo supports is narrow and specific: the baseline is structurally incapable of the maneuver, and Jev supplies it. It is not \"the model makes the drone better at everything\".\nL232: ### What is and is not the model\nL233: \nL234: Worth being precise, because it is easy to overclaim:\nL235: \nL236: layer  | who does it  | rate\nL237: --- | --- | ---\nL238: Awareness - what is out there, how far, where is the target  | numpy on depth + segmentation. Zero Jev.  | 15 Hz\nL239: Flight control - attitude, thrust, mixing  | geometric controller. Zero Jev.  | 500 Hz\nL240: Safety reflex - do not hit that  | code, and it overrides Jev  | 50 Hz\nL241: Tactical choice - over it? around it? which side? is it lost?  | 100% Jev  | ~3 Hz\nL242: Code decides what is there; Jev decides what to do about it. Jev cannot see\nL243: \nL244:   * it takes JSON, not pixels. The defensible claim is \"a judgment model in a live control loop at 3 Hz with 0.11 s median latency\", not \"the model does the perception\".\nL245: ### The judgments themselves are good\nL246: On hand-built scenes, 6 of 7 correct with strong probabilities:\nL247: \nL248:     `LOW BARRIER, all 5 blocked, top 0.45m  -> climb        p=0.93  risk=1.42\nL249:     TALL PILLAR ahead, right wide open     -> gap_right    p=0.72  risk=1.53\nL250:     TALL PILLAR ahead, left wide open      -> gap_left     p=0.40  risk=1.58\nL251:     TARGET GONE 7s, wide open              -> reacquire    p=0.96  lost=0.85\nL252:     BOXED IN, close on all sides, tall     -> brake        p=0.84  risk=1.89\nL253:     ALL CLEAR, target dead ahead           -> hold_course  p=0.82  risk=0.46\nL254:     BRIEF OCCLUSION 0.6s, path clear       -> (muddy, p=0.24)      lost=0.12\nL255:     `\nL256: The one muddy case is instructive: the Choice was unconfident, but the Noul answered it cleanly (`target_truly_lost=0.12`). So the search behaviour is gated on the Noul, not on the Choice. Use the primitive that actually fits the question.\nL257: ### The state has to contain the answer\nL258: \nL259: Jev initially refused to ever pick `climb`. That was correct. The state was five horizontal range sectors - it contained no vertical information at all, so \"fly over it\" was not an inferable option. Adding the obstruction's top-edge height, whether that top edge is visible to the camera, and the aircraft's own climb ceiling moved `climb` from never-chosen to p=0.93.\nL260: That was a state-design bug, not a model failure. It is the single most useful thing this project taught.\nL261: ## Run it\nL262: \nL263:     ./setup.sh                      # venv + fetch the Skydio X2 model\nL264:     cp .env.example .env            # then put your key in it\nL265: \nL266:     set -a && . ./.env && set +a\nL267:     export MUJOCO_GL=glfw           # or egl on a headless box\nL268: \nL269:     .venv/bin/python run.py --seconds 65 --seeds 1              # Jev engaged\nL270:     .venv/bin/python run.py --no-jev --fast --seconds 65 --seeds 0 1 2   # ablation (free)\nL271:     .venv/bin/python run.py --seconds 65 --seeds 1 --video course.mp4    # + telemetry video\nL272:     TRACE=1 .venv/bin/python run.py --seconds 65 --seeds 1      # print every judgment\nL273: A video run also writes `course.mp4.tape.npy`.
