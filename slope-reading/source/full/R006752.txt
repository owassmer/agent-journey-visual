Collect, before interpreting\n\nFor the episode, write three columns and nothing else: what was believed, what\nwas true, and the read that revealed the difference. Use the artifacts —\nevidence files, rulings, command output — not recollection.\n\nSeparate what was verified from what was inferred. An inference that survived\nbecause nobody checked it is the most expensive item on the list, and it is\ninvisible unless the columns are kept apart.\n\n### 2. Classify by transfer, not by cost\n\nFor each row, ask: **does this generalize past the system that produced it?**\n\n| Class | Test | Destination |\n|---|---|---|\n| Universal | Names a class of failure; would recur in an unrelated system | Doctrine |\n| Platform | True of this platform's mechanics; an implementer meets it directly | Platform reference |\n| Project | True of this build's current state | Build state |\n| Instance | One-off, already fixed, no class behind it | Nothing |\n\nInvestigation time is not evidence of importance. A defect that consumed a day\nearns exactly as much doctrine as one that consumed a minute, if they\ngeneralize equally. Recency and sunk effort both inflate perceived weight, and\nneither predicts the future.\n\nMost rows are Platform or Project. One episode rarely earns more than one\nuniversal rule. If it seems to earn three, at least two are the same rule\nobserved from different angles — find the parent and write that.\n\n### 3. Write prescriptively\n\nState what to do. Never narrate what went wrong.\n\n- **Right:** \"Data lands on the default branch; the review branch carries\n  metadata only.\"\n- **Wrong:** \"After four merge failures we discovered that data must land on\n  the default branch.\"\n\nThe failure narrative belongs in the ruling or review record, which is the\narchive. Source-of-truth documents state current facts. A rule that needs its\norigin story to be intelligible is not yet written clearly enough.\n\nApply the same rule to names inside the artifact: no `_v2`, no cycle numbers,\nno slice identifiers in anything the product's users, auditors, or judges will\nmeet. Construction history lives in the development surfaces.\n\n### 4. Convert the rule into a check\n\nA rule nobody enforces is a rule that decays. For each universal or platform\nrule, add the check that would have caught the defect, at the strongest layer\navailable (strongest first):\n\n1. **Structure** — the bad state cannot be expressed.\n2. **Gate** — a mechanical precondition on the action, checked against the\n   system immediately before it.\n3. **Review facet** — a standing question a reviewer asks every cycle.\n4. **Prose** — weakest; use only when the three above are unavailable, and\n   say why.\n\n**State the check generally.** A check written against the exact observed\nfailure catches that failure and no variant of it. Write the class:\n*\"flag any binding whose target exists only in the build environment\"* rather\nthan *\"check the dataset is on master.\"* The specific instance goes in the\nplatform reference as an example.\n\n**Then propagate it to whoever performs the check.** A review facet lives in\ntwo places: the workflow document, and the brief actually handed to the\nreviewer. Updating the first and not the second leaves reviewers certifying\nagainst the previous standard while the workflow claims otherwise — and the\ngap is invisible, because the workflow reads correct.\n\nTreat the reviewer brief as a source-of-truth surface with the same\nmaintenance obligation as doctrine. It carries the contract, the authority to\ncertify completeness against, the governing principles, and the substrate's own\ndocumentation. A reviewer holding only the immediate spec cannot flag a\ncomponent the spec dropped, cannot judge whether the implementation suits the\nplatform, and cannot challenge a deferral, because nothing told them deferrals\nare constrained.\n\n### 5. Prune\n\nFor every addition, look for a deletion. Superseded references, absorbed rules,\nand failure logs masquerading as guidance are removed, not archived in place.\nDoctrine competes for the same attention as the work.\n\n### 6. Verify from the consumer's surface\n\nRe-read each edited document as the agent who will consume it, and confirm the\nold instruction is gone rather than contradicted in a later paragraph. Two\nrules in one file, one correct and one stale, resolve to whichever the reader\nreaches first.\n\n## Ownership\n\nEach source-of-truth surface has exactly one writer.\n\n| Surface | Owner |\n|---|---|\n| Doctrine, review workflow, review facets, specs | Orchestrator |\n| Platform atlas and its references | Implementer |\n| Build state, ledgers, evidence | Implementer, with orchestrator verification |\n\nThe orchestrator does not edit the implementer's platform reference, and the\nimplementer does not edit doctrine. Cross-lane corrections are issued as a\nruling naming the exact text to change.\n\n**Automated writers count as writers.** A self-improvement loop, curator,\nformatter, or dependency bot that edits a source-of-truth surface is a second\nwriter to that surface, and it passes no review gate.
