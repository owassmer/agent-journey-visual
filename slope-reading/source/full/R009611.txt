Modal makes it easy to scale compute across thousands of containers. You won\u2019t have to worry about your App crashing if it goes viral or need to wait a long time for your batch jobs to complete.\nL7: \nL8: For the the most part, scaling out will happen automatically, and you won\u2019t need to think about it. But it can be helpful to understand how Modal\u2019s autoscaler works and how you can control its behavior when you need finer control.\nL9: ## How does autoscaling work on Modal?\nL10: \nL11: Every Modal Function corresponds to an autoscaling pool of containers. The size of the pool is managed by Modal\u2019s autoscaler. The autoscaler will spin up new containers when there is no capacity available for new inputs, and it will spin down containers when resources are idling. By default, Modal Functions will scale to zero when there are no inputs to process.\nL12: Autoscaling decisions are made quickly and frequently so that your batch jobs can ramp up fast and your deployed Apps can respond to any sudden changes in traffic.\nL13: ## Configuring autoscaling behavior\nL14: \nL15: Modal exposes a few settings that allow you to configure the autoscaler\u2019s behavior. These settings can be passed to the `@app.function` or `@app.cls` decorators:\nL16:   * `max_containers`: The upper limit on containers for the specific Function.\nL17:   * `min_containers`: The minimum number of containers that should be kept warm, even when the Function is inactive.\nL18:   * `buffer_containers`: The size of the buffer to maintain while the Function is active, so that additional inputs will not need to queue for a new container.\nL19:   * `scaledown_window`: The maximum duration (in seconds) that individual containers can remain idle when scaling down.\nL20: In general, these settings allow you to trade off cost and latency. Maintaining a larger warm pool or idle buffer will increase costs but reduce the chance that inputs will need to wait for a new container to start.\nL21: Similarly, a longer scaledown window will let containers idle for longer, which might help avoid unnecessary churn for Apps that receive regular but infrequent inputs. Note that containers may not wait for the entire scaledown window before shutting down if the App is substantially overprovisioned.\nL22: ## Dynamic autoscaler updates\nL23: \nL24: It\u2019s also possible to update the autoscaler settings dynamically (i.e., without redeploying the App) using the \ue200cite\ue20297\u2020`Function.update_autoscaler()`\ue201 method:\nL25: \nL26:     `f = modal.Function.from_name(\"my-app\", \"f\")\nL27:     f.update_autoscaler(max_containers=100)`\nL28: The autoscaler settings will revert to the configuration in the function decorator the next time you deploy the App. Or they can be overridden by further dynamic updates:\nL29: \nL30:     `f.update_autoscaler(min_containers=2, max_containers=10)\nL31:     f.update_autoscaler(min_containers=4)  # max_containers=10 will still be in effect`\nL32: A common pattern is to run this method in a \ue200cite\ue20238\u2020scheduled function\ue201 that adjusts the size of the warm pool (or container buffer) based on the time of day:\nL33: \nL34:     `@app.function()\nL35:     def inference_server():\nL36:         ...\nL37: \nL38:     @app.function(schedule=modal.Cron(\"0 6 * * *\", timezone=\"America/New_York\"))\nL39:     def increase_warm_pool():\nL40:         inference_server.update_autoscaler(min_containers=4)\nL41: \nL42:     @app.function(schedule=modal.Cron(\"0 22 * * *\", timezone=\"America/New_York\"))\nL43:     def decrease_warm_pool():\nL44:         inference_server.update_autoscaler(min_containers=0)`\nL45: When you have a \ue200cite\ue20298\u2020`modal.Cls`\ue201 , `update_autoscaler` is a method on an instance and will control the autoscaling behavior of containers serving the Function with that specific set of parameters:\nL46: \nL47:     `MyClass = modal.Cls.from_name(\"my-app\", \"MyClass\")\nL48:     obj = MyClass(model_version=\"3.5\")\nL49:     obj.update_autoscaler(buffer_containers=2)  # type: ignore`\nL50: Note that it\u2019s necessary to disable type checking on this line, because the object will appear as an instance of the class that you defined rather than the Modal wrapper type.\nL51: ## Parallel execution of inputs\nL52: \nL53: If your code is running the same function repeatedly with different independent inputs (e.g., a grid search), the easiest way to increase performance is to run those function calls in parallel using Modal\u2019s \ue200cite\ue20299\u2020`Function.map()`\ue201 method.\nL54: Here is an example if we had a function `evaluate_model` that takes a single argument:\nL55: \nL56:     `import modal\nL57: \nL58:     app = modal.App()\nL59: \nL60: \nL61:     @app.function()\nL62:     def evaluate_model(x):\nL63:         ...\nL64: \nL65: \nL66:     @app.local_entrypoint()\nL67:     def main():\nL68:         inputs = list(range(100))\nL69:         for result in evaluate_model.map(inputs):  # runs many inputs in parallel\nL70:             ...`\nL71: In this example, `evaluate_model` will be called with each of the 100 inputs (the numbers 0 - 99 in this case) roughly in parallel and the results are returned as an iterable with the results ordered in the same way as the inputs.\nL72: ### Exceptions\nL73: \nL74: By default, if any of the function calls raises an exception, the exception will be propagated. To treat exceptions as successful results and aggregate them in the results list, pass in \ue200cite\ue20299\u2020`return_exceptions=True`\ue201 .\nL75: \nL76:     `@app.function()\nL77:     def my_func(a):\nL78:         if a == 2:\nL79:             raise Exception(\"ohno\")\nL80:         return a ** 2\nL81: \nL82:     @app.local_entrypoint()\nL83:     def main():\nL84:         print(list(my_func.map(range(3), return_exceptions=True)))\nL85:         # [0, 1, Exception('ohno'))]`\nL86: ### Starmap\nL87: If your function takes multiple variable arguments, you can either use \ue200cite\ue20299\u2020`Function.map()`\ue201 with one input iterator per argument, or \ue200cite\ue202100\u2020`Function.starmap()`\ue201 with a single input iterator containing sequences (like tuples) that can be spread over the arguments. This works similarly to Python\u2019s built in `map` and `itertools.starmap`.\nL88: \nL89:     `@app.function()\nL90:     def my_func(a, b):\nL91:         return a + b\nL92: \nL93:     @app.local_entrypoint()\nL94:     def main():\nL95:         assert list(my_func.starmap([(1, 2), (3, 4)])) == [3, 7]`\nL96: ### Gotchas\nL97: \nL98: Note that `.map()` is a method on the modal function object itself, so you don\u2019t explicitly call the function.\nL99: \nL100: Incorrect usage:\nL101: \nL102:     `results = evaluate_model(inputs).map()`\nL103: \nL104: Modal\u2019s map is also not the same as using Python\u2019s builtin `map()`. While the following will technically work, it will execute all inputs in sequence rather than in parallel.\nL105: \nL106: Incorrect usage:\nL107: \nL108:     `results = map(evaluate_model, inputs)`\nL109: ## Asynchronous usage\nL110: \nL111: All Modal APIs are available in both blocking and asynchronous variants. If you are comfortable with asynchronous programming, you can use it to create arbitrary parallel execution patterns, with the added benefit that any Modal functions will be executed remotely. See the \ue200cite\ue20293\u2020async guide\ue201 or the examples for more information about asynchronous usage.\nL112: ## GPU acceleration\nL113: \nL114: Sometimes you can speed up your applications by utilizing GPU acceleration. See the \ue200cite\ue20226\u2020GPU section\ue201 for more information.\nL115: ## Scaling Limits\nL116: \nL117: Modal enforces various platform limits that affect scalability. Limits on the total number of concurrent containers (and the total number of GPUs in concurrent use) depend on your workspace\u2019s \ue200cite\ue202101\u2020plan level\ue201 . There is also a hard limit of 4,000 concurrent containers running for a single Function.
